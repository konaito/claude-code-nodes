# PTY の起動直後の入力、端末の SSE のまとめ方、一覧の取り方（2026-11-12）

#26、#25、#24 を直し、#22 は測ってから実装を止めた。試験は試験用のノードで行った。konaito-pro では 127.0.0.1:4431、vm では同じポートに立て、どちらも別の `CCN_CONFIG` を使った。常駐の 4323 には触っていない。claude は 2.1.322（konaito-pro）、model は haiku である。

23:00〜23:07 に konaito-pro で claude を10本同時に動かす測定をした。このとき konaito-pro の load average は22まで上がり、本番の一覧が1秒を超えた。本人の Claude Town は一覧を3秒で打ち切り、町が空になった。以後、claude を何本も同時に立てる測定は vm か incertotech で行い、同時に4本までにする。

## #26 作成の直後の send が送信されない

### 原因

PTY の claude を起動すると、SessionStart の hook は約0.9秒で届く。claude が入力を読み始め、`ESC[?2004h`（bracketed paste の有効化）を出すのは、負荷の無いときで約1.1秒、4本を同時に起動したときで1.3〜2.4秒だった。send は SessionStart だけを待っていたので、その間に貼り付けと Enter を書いていた。貼った文は入力欄に入るが、Enter は捨てられる。失敗した回では、claude の最初の描画にもう本文が入っていた。

試験用のノードに、hooks の到着、貼り付け、出力の列の時刻を書く一時的な記録を入れて測った（コミットしていない）。

| セッション | SessionStart と貼り付け | `ESC[?2004h` | `ESC[?1049h` |
| --- | --- | --- | --- |
| f6db9f8a | 920ms | 2416ms | 2583ms |
| 851b0ea8 | 948ms | 1885ms | 2106ms |
| 8c50a9ed | 990ms | 1345ms | 1412ms |
| 899c41ad | 1020ms | 1377ms | 1446ms |

4本とも送信されなかった。

### 直し方

- send は、SessionStart と `ESC[?2004h` の両方を待つ。SessionStart も待つのは、信頼の確認の画面で Enter を押して、信頼に答えないためである。信頼の確認の画面でも `ESC[?2004h` は出る（macOS で 0.70秒、vm で 1.02秒）。
- 端末の口の入力（`POST …/terminal/input`）は、`ESC[?2004h` が出るまでノードで溜め、出たら順に流す。Claude Town の「新しい世帯」は、最初の出力の300ms後に terminal/input で文と `\r` を送る。最初の出力（約0.8秒）は `ESC[?2004h` より前に出るので、同じ不具合に当たっていた。
- claude の版が変わって `ESC[?2004h` が出なくなったときのために、起動から10秒たったら溜めた入力を流す。send もそこから先へ進む。

### 前後の数字

作成の直後（待たずに）送り、`user`、`assistant`、`result` の3つがそろうかを見た。1回に4本を同時に立てた。

| 送り方 | 直す前 | 直した後 |
| --- | --- | --- |
| send（`POST …/messages`） | 単発では20回中1回失敗。4並列では計24回中22回失敗 | 4並列で計20回中20回届いた |
| Claude Town と同じ terminal/input | 4並列で8回中7回失敗 | 4並列で計20回中20回届いた |
| resume した PTY に send | （測っていない） | 単発で3回中3回届いた。send は約1.0秒で返った |

`ESC[?2004h` を待つ試しの版では、貼り付けから Enter までの待ち（既定 150ms）を0にしても8回中8回届いた。貼り付けと Enter が1回の読み出しにまとまること自体は原因ではない。

vm（Linux、bun 1.4.4）では、信頼していないディレクトリに PTY を立てて確かめた。作成の直後に terminal/input で下キーを送ると、200 がすぐ返った。下キーは溜められ、`ESC[?2004h`（1.02秒）の後に届いて、信頼の確認の選択が動いた。send は SessionStart を待ち、10秒で 409 になった。信頼の確認には答えていない。vm には信頼済みのディレクトリが無いので、vm での send の往復は確かめていない。

## #25 端末の SSE の data をまとめる

前の data から 17ms 以上空いていればすぐ送り、詰まっていれば次の 17ms の区切りでまとめて送るようにした。1秒あたりの data は60回以下になる。size、exit、新しい画面の attach の前には、溜めた分を先に送る。data の形（`{b64}` と、末尾のバイト位置の `id`）は変えていない。見ている画面が無いときは、base64 も作らない。

本物の claude に500語の物語を書かせ、その間の data を数えた。

| | 1秒あたりの最大 | 1秒あたりの平均 | バイト位置の飛び |
| --- | --- | --- | --- |
| 直す前（3回） | 18、20、18 | 11.7、10.7、9.8 | 0 |
| 直した後（3回） | 18、16、18 | 10.0、11.0、10.5 | 0 |

直す前から60回以下で、ほとんど変わらなかった。claude は自分で描画の回数を絞っているためである。まとめが効くのは、claude の外の出力（Ctrl+G で開くエディタなど）が詰まって届くときになる。この場面は測っていない。

WebSocket のバイナリの口は作らなかった。claude 1本の出力は1秒あたり約3〜4KB で、base64 で増える量は小さい。SSE は中継と Access の道をそのまま通れる。

## #24 一覧の取り方（23:06 の件）

### 何が起きた

23:06 に、本人の Claude Town（安定版）が `/api/sessions` を3秒で打ち切り、「ccn につながらない」と出して町が空になった。親 meta-9d が本番の konaito-pro のノード（8b187f1）を測ると、一覧の応答は 0.002〜1.41 秒で、ノードの CPU は10秒で2.0秒だった。

### 原因

`/api/sessions` は、一覧の材料を2秒のメモリキャッシュに置いていた。材料は、SDK の `listSessions`（終わったセッション）と `claude agents --json`（端末のセッション）である。キャッシュが切れると、要求はこの2つを取り直すまで待つ。Claude Town は一覧を2秒ごとに呼ぶので、ほぼ毎回待っていた。

konaito-pro の `~/.claude/projects` には jsonl が8024個（14GB）ある。`listSessions({limit: 100})` を単体で3回測ると、実時間は105〜113ms、CPU は265〜383ms、イベントループの詰まりは最大14〜30ms だった。`claude agents --json` は実時間0.22〜0.25秒だった。上の負荷で機械が混んでいたので、この待ちが1秒を超えたと見ている。

node.log の TimeoutError（2件）は、22:19 より前に Cloudflare API につながらなかったときの記録で、この件とは別と見ている。

### 直し方

一覧の材料は、古くなっても要求を待たせずに古い値を返し、裏で1回だけ取り直す。取り直しに失敗したら古い値を使い続ける。初めての要求だけは取れるまで待つ。その取得に失敗したら覚えず、次の要求で取り直す。取り直しの間隔は、端末のセッションが2秒、終わったセッションが15秒である。

### 前後の数字

試験用のノードに、Claude Town と同じく2秒ごとに `/api/sessions` を30回送った。このとき claude は立てていない。

| | 件数 | 最初の1回 | 中央値 | 90%点 | 最大 | ノードの CPU |
| --- | --- | --- | --- | --- | --- | --- |
| 直す前（8b187f1） | 101 | 420ms | 351ms | 415ms | 524ms | 14.2% |
| 直した後 | 100 | 361ms | 1ms | 3ms | 361ms | 3.1% |

終わったセッションは、最大15秒遅れて一覧に出る。ノードが立てた子は、終わってから30分は台帳に残るので、この遅れは見えない。人が端末で閉じたセッションは、一覧から消えるのが最大15秒遅れる。
