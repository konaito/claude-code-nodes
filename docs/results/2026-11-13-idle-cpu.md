# 待機中のノードの CPU（#23、2026-11-13）

## 結論

呼び手が無い待機では、ノードの CPU は直す前から 0.08% だった。#23 の約7%は、Claude Town の呼び出しを処理する分である。

Claude Town と同じ呼び方で測ると、直す前のノード自身の CPU は 5.2〜7.2% だった。会話の件数と会話の続きを毎回 jsonl から読み直していたのが主な原因で、件数を覚えるようにした後は 1.7〜3.2% になった。1% 未満には届いていない。残りは `claude agents --json` の起動と、終わったセッションの一覧の取り直しである。

ノードが一覧の材料として起動する `claude agents --json` の CPU は、子のプロセスの分なので ps のノードの値に入らない。1回 0.26〜0.27 秒（user と sys の和、5回）で、1分に15回（約4秒に1回）起動していた。2秒の取り直しの間隔が切れた後の要求で起動するので、2秒ごとの呼び出しでは約4秒に1回になる。機械全体では1コアの約6.7%にあたり、この PR では減らしていない。

## 測り方

- 機械は konaito-pro（macOS、Bun 1.3.11）。測っている間の load average は 4.5〜17 で、ほかの子の作業で混んでいた。
- 試験用のノードを別の設定（`/tmp/ccn-perf/ccn.json`、名前 perf-idle、127.0.0.1:4471、受け口は /private/tmp/ccn-perf/lobby）で立てた。Access と登録簿は無い。`CLAUDE_CONFIG_DIR` を外し、本番の常駐と同じ `~/.claude` を読ませた。jsonl は約13,600個（14GB）ある。
- `scripts/bench-idle.ts` がノードを立て、最初の一覧を1回取ってから3秒待ち、60秒間のノードの CPU 時間を `ps -o time` の差で測る。子のプロセスは50ミリ秒ごとの `pgrep -P` で数える。
- 呼び方は Claude Town（konaito/ClaudeTown の feat/app-v1）と同じにした。`GET /api/sessions` を2秒ごと（`POLL_MS`）、開いた会話の `GET /api/sessions/<id>/messages?after=<next>` を2.5秒ごと（`CONV_POLL_MS`）、承認の欄の `GET /api/sessions/<id>` を2秒ごと。
- 前後の比べでは、開いた会話に端末のセッションを3つ使った。jsonl が伸びているもの（sidenote ASO、6.4MB、60秒で約3万〜15万バイト伸びた）と、meta-ff（8.8MB。直す前の1回目の間だけ約7,500バイト伸び、ほかの回は止まっていた）と、測定中は止まっていた自分のセッション（1.3MB）である。
- 呼び方を1つずつ分けた測定と `bun --cpu-prof` には、meta-9d（11.9MB、測定の間に約3万バイト伸びた）を使った。
- 直す前は origin/main の fe5908c、直した後はこのブランチである。

## 数字

ノード自身の CPU（60秒、ps）。

| 呼び方 | 直す前 | 直した後 |
| --- | --- | --- |
| 呼び手なし | 0.08% | 0.08% |
| 一覧だけ | 2.43% | 1.17% |
| Claude Town と同じ（伸びている会話） | 7.18%、6.77% | 2.20%、1.72% |
| Claude Town と同じ（meta-ff） | 5.20%、5.22% | 3.20%、1.67% |
| Claude Town と同じ（自分のセッション） | 5.90%、5.98% | 2.32%、3.10% |

直す前と後は、伸びている会話の行だけが同じ時間帯で交互に測ったものである。ほかの行は、直す前を 00:40〜00:45、直した後を 00:59〜01:05 に測った。同じ条件の2回で 1.5 ポイントほど違うことがあり、機械の混み方の影響が大きい。

応答の中央値（伸びている会話、直す前 → 直した後）は、messages が 34〜59ms から 1.8〜2.3ms、詳細が 40〜66ms から 2.4〜2.8ms になった。

直す前に呼び方を1つずつ分けて40秒ずつ測ると、ノード自身の CPU は一覧が 2.47%、messages が 2.60%、詳細が 3.05% だった。

`bun --cpu-prof` の標本（Claude Town と同じ呼び方、直す前、1865標本）では、自分の時間の上位が `JSON.parse`（596）、`toString`（336）、`indexOf`（160）、`copy`（112）で、どれも SDK が jsonl を読んで解析する処理だった。`--cpu-prof-md` の表の秒数は待ち時間を含むので使っていない。標本は約1.9秒分で、ps の値（4.4秒）との差は JS の外（spawn、GC、入出力）にあたる。

## 原因

- 詳細（`GET /api/sessions/<id>`）は、`cursor` を出すために、2秒ごとに `getSessionMessages(id)` で会話を全部読んで数えていた。
- 会話（`messages?after=`）は、新しい行が無くても2.5秒ごとに `getSessionMessages` を呼んでいた。SDK は offset と limit を付けても jsonl を全部読む。
- どちらも dir を渡していないので、SDK は約980個のプロジェクトのディレクトリを探していた。`getSessionInfo` は dir なしで1回 7.2ms、dir ありで 1.3ms、`getSessionMessages` は 11.9MB の会話（meta-9d）で dir なしが 52ms、dir ありが 34ms だった（CPU 時間、5回の平均）。
- 一覧は、終わったセッションの `listSessions`（1回 CPU 約300ms）を15秒ごとに取り直していた。

## 応答が変わっていないこと

直す前（fe5908c）と直した後のノードを 127.0.0.1:4471 と 4472 に並べて立て、同じ要求の応答を比べた。直した後のノードには同じ要求を先に1回送り、件数と dir を覚えさせてから比べた。比べたのは、詳細（`lastActivityAt` と `startedAt` を除く全体）、`messages?after=0`、`after=<cursor>`、`after=<cursor-1>`、`after=<cursor+5>` の状態コード、uuid の列、`next` と応答の全体である。対象は、終わったセッション1つ（8f14b5aa、179件）、端末のセッション2つ（meta-9d の631件、meta-ff の246件）、無い UUID と UUID でない id で、違いは0件だった。

## 直したこと

- `History`（`src/engine/history.ts`）が、会話ごとに件数と jsonl の印を覚える。印は `getSessionInfo` の `lastModified` と `fileSize` である。印が同じなら件数を数え直さない。after が覚えた件数以上なら、会話を読まずに空を返す。印を先に取ってから読むので、読む間に jsonl が伸びても、次の呼び出しで印が変わって読み直す。`fileSize` が無いときは覚えない。覚えるのは件数と印だけで、解析した会話は持たない。上限は256件。
- 最初に `getSessionInfo` で分かった cwd を、次から dir として渡す。dir で見つからなければ dir なしで探し直す。
- 終わったセッションの一覧の取り直しを15秒ごとから60秒ごとにした（`src/api/sessions.ts` の `HISTORY_MS`）。端末のセッションが `claude agents --json` から消えたときと、DELETE でセッションを台帳から消したときは、60秒を待たずに次の要求で取り直す。

## 遅れの出方

- ノードが立てた子は、終わってから30分は台帳に残るので、一覧の遅れは見えない。DELETE で止めた子はすぐ台帳から消えるので、そのときも次の要求で一覧を取り直す。
- 人が端末で閉じたセッションは、agents から消えた次の要求で一覧を取り直すので、遅れは今と同じく数秒である。
- agents にも台帳にも出ないセッション（`claude -p` を端末で直接動かしたものなど）は、一覧に出るのが最大60秒遅れる。

## 残り

- `claude agents --json` を1分に15回起動している。ノード自身の CPU では、一覧だけの 1.17% の多くがこの起動と出力の読み取りにあたると見ているが、標本では分けていない。子のプロセスの分は機械全体で約6.7%ある。#24 で、一覧に状態の絞り込みと変化を流す SSE を足すときに、`claude agents` を呼ぶ間隔と、呼ぶのを購読がある間だけにする形を決める。
- Claude Town が一覧を `?state=live` で取るようになれば、終わったセッションの `listSessions` は呼ばなくて済む（#24）。
- 本番のノードには配っていない。本番での前後の値はまだ無い。
