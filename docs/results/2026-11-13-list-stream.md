# 一覧の絞り込み、ETag、変化の SSE（#24、2026-11-13）

## 結論

Claude Town が一覧を `GET /api/sessions/stream?state=live` の SSE で受けるように替えると、一覧の要求は1分に0回になる。一覧が流れてきたのは1分に2〜5回だった。#24 の終わりの条件（待機中の一覧の要求が1分に数回以下）は、Claude Town が乗り替えれば満たせる。

Claude Town の今の呼び方（一覧、会話、詳細）のままだと、ノード自身の CPU は直す前（999b52e）とほぼ同じだった。一覧を SSE に替えた呼び方では、1.77〜2.38% から 1.30〜1.40% に下がった。`claude agents --json` の起動は、1分15回から12〜13回になった。1% 未満には届いていない。

## 測り方

- #23 と同じ `scripts/bench-idle.ts` で、試験用のノード（127.0.0.1:4471、Access なし、`~/.claude` を読む）を立て、60秒間のノードの CPU 時間を ps で測った。機械は konaito-pro で、load average は 10〜21 だった。
- `stream` の呼び方を足した。一覧は `GET /api/sessions/stream?state=live` を1本つなぐだけにし、会話（2.5秒ごと）と詳細（2秒ごと）は Claude Town の今の間隔で呼ぶ。
- 開いた会話は端末のセッション sidenote ASO（7.2MB）。測っている間はほとんど伸びていなかった。
- 直す前は origin/main の 999b52e（#23 を入れた版）。直す前と後を交互に2回ずつ測った。

`claude agents --json` の起動は1回 CPU 0.26〜0.27 秒（#23 で測った値）なので、1分13回で機械全体の約5.8%にあたる。この分は上のノードの CPU に入っていない。

## 確かめたこと

- 試験用のノードに `curl -N` で SSE をつないで20秒、`claude agents` の起動は7回だった（最初の一覧の分と、4秒ごとの取り直し）。curl を止めた後の20秒は0回で、見張りは止まった。
- Last-Event-ID に今の ETag を付けてつなぐと、最初の一覧は来ないが、応答のヘッダは約15ms で届いた。中継の15秒の時間切れには当たらない。
- 試験（`test/api/list-stream.test.ts`、`test/relay/relay.test.ts`）で確かめたこと。絞り込みで exited を除くと `listSessions` を呼ばない。知らない状態は 400。ETag が同じなら 304 で本文なし、`W/` を付けても同じ。台帳の状態の変化は tick を待たずに届く。端末のセッションの変化は tick で届く。変わらなければ流さない。見張りの間は一覧と詳細の要求が `claude agents` を起動しない。遅い取り直しの途中で抜けて入り直しても、tick の連鎖は1本のまま。中継は `If-None-Match` を相手へ、`ETag` と 304 を呼び手へ運ぶ。

- 本番のノードには配っていない。
- ノードが立てた子と PTY が動いている間は、`lastActivityAt` が変わるので、約4秒ごとに一覧が流れる。何本も動いているときの流れる回数は測っていない。
