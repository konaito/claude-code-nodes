# エージェントが立てた子を、手が空いたら自動で止める（#44）

## 作ったもの

parent が `agent:` で始まる node と pty のセッションは、ターンが終わって idle のまま `idleStopMinutes`（設定、既定10分、0 で止めない）を過ぎると、ノードが止める。会話は残り、`create_session resume=<id>` で続けられる。

- 止めないのは、作業中、承認待ち、端末の画面が開いている間、人が立てたセッション（parent が `local` か email）、端末のセッション、1通目を待っているセッション。
- 最後の動きは `lastActivityAt`（send、端末の入力、hooks）と、pty の端末の画面の接続と切断の時刻。
- 止める直前に `claude agents --json` で claude が busy でないかを確かめる。
- タイマーはセッションごとに1本で、台帳が idle への変化を見たときに張る。毎秒の見回りはしない。
- 理由は `exitReason` の `idle-stop: ...` に入る。台帳から掃いた後も256件まで覚え、一覧と詳細の過去分に重ねる。MCP の `list_sessions` は止めてから1日の間は既定の一覧に出し、`read_messages` は `[exited] <理由>` の行を出す。

## 直した既存の不具合

端末の SSE が切れても、購読は claude が次に何か出すまで外れなかった。`sse()` の `cancel` が呼ぶ `it.return()` は、次の枠を待って止まっているジェネレーターには届かないためである。待機中の claude は何も出さないので、画面を閉じた子が開いたままと数えられ、止まらなかった。`sse()` に `onCancel` を足し、端末の口は購読のキューを直接閉じるようにした。

## 実機で確かめたこと

2026-11-13、konaito-pro で #44 の版のノードを 4393 番、`idleStopMinutes: 0.5`（30秒）で立てた。どれも cwd はこのリポジトリの pty の子で、最初の文は「Reply with just the word: hi」。`/tmp/ccn-measure/live.ts` が1秒ごとに詳細を読んだ。

| 試し方 | 結果 |
| --- | --- |
| parent が agent の子 | idle になってから32.1秒で exited。一覧の `exitReason` は `idle-stop: no activity for 0.5 min; ...`。同じ id を `terminal: true` と `resume` で立て直すと 201 で idle に戻った。次の文で前の返事を聞くと「hi」と答えた |
| parent が local の子 | idle のまま60秒たっても止まらなかった |
| parent が agent で、端末の画面を開いた子 | 開いている50秒の間は止まらなかった。修正前は閉じてからも180秒止まらなかった。修正後は閉じてから44.1秒で exited になった |

画面を閉じてから止まるまでが30秒より長いのは、ノードが切断に気づくのが次の keep-alive（15秒ごと）を書いたときだからとみている。中継（`/n/<peer>/...`）越しの切断は試していない。

## 親から頼まれた別の症状（messages から assistant の文が返らない）

子 ct-merge-prs（01c06dc4、pty）で、16:56〜16:58 の assistant の行の一部が `messages` から返らなかった。このセッションは 16:44 に新しく立ち、17:13 まで1つのターンで動いていた。途中の resume は無い。当時のノードは #43 の修正（17:15 にインストール）より前のコードだった。

- 今の jsonl に SDK の `getSessionMessages` を当てると、assistant と道具の結果の行は全部返った。返らないのは画像の補足の meta 行9件だけで、ノードはもともと流さない。
- jsonl を先頭から1行ずつ伸ばした写しを `CLAUDE_CONFIG_DIR` の下に置き、16:50〜17:00 の199通りで SDK を当てた。assistant と道具の結果の行が、途中の時点で一時的に抜けることも無かった。
- 当時のコードは PostToolUse と承認と Stop のときだけ読んだ。16:56:21〜16:56:23 の thinking と Bash の tool_use は、その Bash が終わる 16:57:07 まで約45秒読まれなかった計算になる。

欠けではなく遅れで、原因は #43 と同じとみている。生きていた間の台帳はノードの再起動で消えているので、当時の messages の応答そのものは確かめていない。
