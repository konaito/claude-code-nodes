## 受け口の許可（.claude/settings.json）

前の試しでは、default の受け口に1件の依頼で8回の承認が要った。受け口のディレクトリに許可を置き、手順の書き方も直した。測った claude は 2.1.322、設定ディレクトリは `CLAUDE_CONFIG_DIR=~/.cam/profiles/agent`（本番の常駐とは別）。

### 実装の前に確かめたこと

`claude -p --permission-mode default` を未信頼のフォルダで動かし、無害な命令（`probe`、呼ぶと /private/tmp に1行足す sh）を許す規則の置き場を比べた。

| --- | --- |

| 命令 | 結果 |
| --- | --- |
| roots の下を指す `ls`、`head`、`cat`（`Read(//<root>/**)` あり） | 通った。Read の許可が無い回では、作業ディレクトリの外として止まった |

## 秘密の置き場の deny と承認の中身

前の節の「確かめていないこと」に残した2つを直した。roots がホームだと秘密の置き場まで承認なしで読めること、子の承認に説明文しか出ないことである。

### 置く deny

公式の文書（https://code.claude.com/docs/en/permissions）で次を確かめてから書いた。

- 規則は deny、ask、allow の順に評価され、最初に当たったものが使われる。allow で deny に穴を開けることはできない。
- Read の規則は gitignore の書き方で、`//` は絶対パス、`/` が1本だと設定の置き場からの相対になる。`//**/.env` はファイルシステムのどこにある `.env` にも当たる。
- Read の deny は、Edit と Write、Bash の `cat`、`head`、`tail`、`sed` などにも当たる。ファイル名を書かずに読む命令（`grep -r`）と、ファイルを自分で開くスクリプトには当たらない。
- deny は bypassPermissions でも効く（https://code.claude.com/docs/en/permission-modes）。

roots とノードのホームのそれぞれを基点に、次を `Read` の deny にする。ホームも基点にするのは、roots がホームでない機械や、allow が効かない bypassPermissions の受け口でも塞ぐためである。

| 種類 | 規則 |
| --- | --- |
| 基点の下のディレクトリ | `.ssh`、`.gnupg`、`.aws`、`.cloudflared`、`.config/ccn`、`.config/cc`（改名前の設定）、`.config/gh`、`Library/Keychains`（それぞれ `/**`） |
| 基点の下のファイル | `.netrc`、`.claude/.credentials.json` |
| どこにあっても | `//**/.env`、`//**/.env.*`、`//**/*.pem`、`//**/*.key` |
| 読んでいる設定 | `CCN_CONFIG` で既定の置き場の外の設定を読んでいるときは、そのファイルと隣の `tunnel.token` |

依頼にあった置き場に、`.config/cc`、`.config/gh`、`.claude/.credentials.json` と、`CCN_CONFIG` の設定を足した。試験（`test/lobby/lobby.test.ts`）では、各基点に全部の項目があること、規則がすべて `//` で始まる Read であること、allow に秘密の置き場を名指しする規則と `!` の否定が無いことを固定した。

### 承認の中身の表示

`src/sessions/pending.ts` の `describePending` が、承認待ちを1行にする。`ccn show` の `pending:`、`ccn read` の `[permission]`、MCP の `read_messages` の `[permission]` と `[pending]`、`get_session` の `shown` は、すべてこの関数の出力を使う。

- Bash は `command`、Write、Edit、MultiEdit、Read は `file_path`、NotebookEdit は `notebook_path` を出す。ほかの道具は `url`、`pattern`、`path`、`query` などの主な値を出し、当たる値が無ければ入力を JSON で出す。
- 値は JSON の文字列の書き方で逃がす。改行は `\n` になるので、命令の中に偽の `pending:` 行を書いても1行に収まる。逃がすのは値の中だけで、`ccn read` に混じる子の文は逃がさない。子は `[permission]` に似た行を書けるので、ひな形では許す前に `ccn show` の `pending:` で確かめるようにした。
- 400字を超える値は切り、`…(+N字)` を付ける。入力が無いときは `(中身なし)` と出す。
- 子が書いた説明文は `("…")` として後ろに付ける。
- `get_session` の `input` は、文字列の値を2000字で切って返す。Write の content を丸ごと返さないためである。

受け口のひな形の「子の承認に答える」には、中身で判断し、説明文を判断の材料にしないことを書いた。`(中身なし)`、`…(+N字)`、読み取れない命令のときは deny する。

## places が macOS の保護フォルダで止まる件

PR #15 を本番の3台に配った直後、incertotech（macOS の Mac mini、launchd の常駐の bun、port 4323）だけ `/api/places` が返らなかった。入口経由では 524 になった。ノードの中から 127.0.0.1:4323 を叩いても60秒応答しなかった。同じノードの `/api/host` は0.04秒で返った。konaito-pro と vm は返った。

### 見立て（未確認）

`sample` で見ると、ノードのスレッドが openat で止まり続けていた。incertotech の TCC.db には bun の記録が1件も無かった。places はホーム（roots）の直下の Desktop、Downloads、Pictures などを readdir していた。そのため、フォルダの承認（TCC）の待ちでファイル操作が返らないとみている。画面のダイアログは見ていない。止まったスレッドが呼ぶたびに増え、ノード全体のファイル操作が止まるおそれも確かめていない。

### 開かない場所の一覧と根拠

ホームの直下で開かない場所を `src/lobby/places.ts` の `MAC_PROTECTED` に置いた。macOS（darwin）のときだけ効く。

| 場所 | 根拠 |
| --- | --- |
| Desktop、Downloads | Apple Platform Security の「Controlling app access to files in macOS」。同意が要る場所として Documents、Downloads、Desktop、iCloud Drive、ネットワークのボリュームを挙げている。この Mac（macOS 27.0.1）の TCC.framework の文言にも `kTCCServiceSystemPolicyDesktopFolder`、`DownloadsFolder` がある |
| Library | iCloud Drive（`Library/Mobile Documents`）は同じ文書にある。TCC.framework の文言に、ほかのアプリのデータ（`kTCCServiceSystemPolicyAppData`）と FileProvider（`kTCCServiceFileProviderDomain`）がある。もとから秘密の置き場（`Library/Keychains`）を含むので候補にしていなかった |
| Pictures、Music | TCC.framework の文言に、写真ライブラリ（`kTCCServicePhotos`）とミュージックのライブラリ（`kTCCServiceMediaLibrary`）がある。フォルダそのものが対象だという根拠は無い |
| Movies、Public、Applications、iCloud Drive | TCC の対象だという根拠は無い。行き先にならない標準のフォルダなので外した。iCloud Drive は利用者が置く symlink の名前である |
| /Volumes（symlink の先） | 同じ文書の表に、取り外しのボリュームとネットワークのボリュームがある |

Documents も TCC の対象（`kTCCServiceSystemPolicyDocumentsFolder`）だが、受け口の主な行き先なので外していない。roots に保護フォルダそのもの（たとえば `~/Desktop`）を選んだときは、その下を読む。

### 直し方

- 飛ばす判定は、パスの字面で、そのパスに fs を当てる前に行う。保護フォルダには readdir、stat、realpath のどれも当てない。symlink は readlink で先を字面で解き、先が保護フォルダか秘密の置き場なら realpath も当てない。
- places の fs の呼び出しには、1回ごとに1秒、走査全体に3秒の上限を付けた（`PLACES_OP_MS`、`PLACES_DEADLINE_MS`）。時間切れのときは、それまでに読めた候補を返す。返り値には `partial: true`、読めなかった場所の `unreadable`、英文の `note` を足す。CLI は「一部のフォルダを読めなかった（時間切れ）」の行を出す。MCP の `list_places` は `partial` と `unreadable` を写し、`note` に足す。
- 呼び出し1回の上限を超えたパスは、ノードが動いている間は覚えておき、その下も開かない（`PlacesMemory.stuck`）。全体の時間切れで待ちを切っただけのものは、遅いだけかもしれないので覚えない。その代わり、呼び出しが返るまではそのパスに次の呼び出しを出さない（`PlacesMemory.pending`）。どちらでも、止まったスレッドは1つのパスに1つまでで、呼ぶたびには増えない。
- 走査は `PlacesScanner` が1つにまとめる（single-flight）。進んでいる走査があれば、同時の呼び出しはそれを待つ。終わった走査の結果は10秒使い回す。前の作りは、走査を始めた時刻から10秒で作り直すので、走査が返らないと10秒ごとに新しい走査が増える作りだった（コードを読んで分かったことで、本番では数えていない）。
- 候補の README と `.git` は8件ずつ読む。前の作りは全候補を同時に開いていた。
- セッションの cwd の symlink を解く処理も同じ見張りの下に置いた。roots の外と保護フォルダの中の cwd は解かない。

- 直した版で incertotech の places が返ること。本番には配っていない。
