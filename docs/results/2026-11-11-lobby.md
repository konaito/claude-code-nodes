## 受け口の許可（.claude/settings.json）

前の試しでは、default の受け口に1件の依頼で8回の承認が要った。受け口のディレクトリに許可を置き、手順の書き方も直した。測った claude は 2.1.322、設定ディレクトリは `CLAUDE_CONFIG_DIR=~/.cam/profiles/agent`（本番の常駐とは別）。

### 実装の前に確かめたこと

`claude -p --permission-mode default` を未信頼のフォルダで動かし、無害な命令（`probe`、呼ぶと /private/tmp に1行足す sh）を許す規則の置き場を比べた。

| 規則の置き場 | 結果 |
| --- | --- |
| `.claude/settings.json` | 使われない。stderr に `Ignoring 1 permissions.allow entry from .claude/settings.json: this workspace has not been trusted.` が出た |
| `.claude/settings.local.json` | 使われた |
| `--settings <file>` | 使われた |

公式の文書（permissions の「What runs before you trust a folder」）にも、`claude -p` と SDK のセッションは project の `permissions.allow` を使わないとある。そこでノードは、cwd が受け口のセッション（resume を含む）にだけ、同じ `.claude/settings.json` を SDK の `settings` でも渡す。

規則があっても止まる書き方も、同じ方法で調べた（Read の許可を足した回）。

| 命令 | 結果 |
| --- | --- |
| roots の下を指す `ls`、`head`、`cat`（`Read(//<root>/**)` あり） | 通った。Read の許可が無い回では、作業ディレクトリの外として止まった |
| `git -C <dir> remote -v`、`git -C <dir> log` | 止まった |
| `for d in …; do …; done`、`probe show $CLAUDE_CODE_SESSION_ID` | 「変数を確かめられない」で止まった |
| `probe allow x; probe read y; echo "exit=$?"` | `echo "exit=$?"` で止まった |
| `ls ~/Documents \| head -3` | 止まった |

前の8回の多くは、この書き方によるものだった。ひな形には「1回の Bash に1命令、変数と `~` を使わず絶対パス、remote は `.git/config` を読む」と書き、`~/Documents` は描画のときに絶対パスにした。自分の権限モードは `ccn show`（対象なし）で読めるようにした。

### 置く許可

roots が `/Users/konaito` のときの中身は次のとおり。

```json
{
  "permissions": {
    "allow": [
      "Bash(ccn peers *)", "Bash(ccn ls *)", "Bash(ccn show *)", "Bash(ccn new *)", "Bash(ccn run *)",
```

## 秘密の置き場の deny と承認の中身

前の節の「確かめていないこと」に残した2つを直した。roots がホームだと秘密の置き場まで承認なしで読めること、子の承認に説明文しか出ないことである。

### 置く deny

公式の文書（https://code.claude.com/docs/en/permissions）で次を確かめてから書いた。

- 規則は deny、ask、allow の順に評価され、最初に当たったものが使われる。allow で deny に穴を開けることはできない。
- Read の規則は gitignore の書き方で、`//` は絶対パス、`/` が1本だと設定の置き場からの相対になる。`//**/.env` はファイルシステムのどこにある `.env` にも当たる。
- Read の deny は、Edit と Write、Bash の `cat`、`head`、`tail`、`sed` などにも当たる。ファイル名を書かずに読む命令（`grep -r`）と、ファイルを自分で開くスクリプトには当たらない。
- deny は bypassPermissions でも効く（https://code.claude.com/docs/en/permission-modes）。

roots とノードのホームのそれぞれを基点に、次を `Read` の deny にする。ホームも基点にするのは、roots がホームでない機械や、allow が効かない bypassPermissions の受け口でも塞ぐためである。

| 種類 | 規則 |
| --- | --- |
| 基点の下のディレクトリ | `.ssh`、`.gnupg`、`.aws`、`.cloudflared`、`.config/ccn`、`.config/cc`（改名前の設定）、`.config/gh`、`Library/Keychains`（それぞれ `/**`） |
| 基点の下のファイル | `.netrc`、`.claude/.credentials.json` |
| どこにあっても | `//**/.env`、`//**/.env.*`、`//**/*.pem`、`//**/*.key` |
| 読んでいる設定 | `CCN_CONFIG` で既定の置き場の外の設定を読んでいるときは、そのファイルと隣の `tunnel.token` |

依頼にあった置き場に、`.config/cc`、`.config/gh`、`.claude/.credentials.json` と、`CCN_CONFIG` の設定を足した。試験（`test/lobby/lobby.test.ts`）では、各基点に全部の項目があること、規則がすべて `//` で始まる Read であること、allow に秘密の置き場を名指しする規則と `!` の否定が無いことを固定した。

### 承認の中身の表示

`src/sessions/pending.ts` の `describePending` が、承認待ちを1行にする。`ccn show` の `pending:`、`ccn read` の `[permission]`、MCP の `read_messages` の `[permission]` と `[pending]`、`get_session` の `shown` は、すべてこの関数の出力を使う。

- Bash は `command`、Write、Edit、MultiEdit、Read は `file_path`、NotebookEdit は `notebook_path` を出す。ほかの道具は `url`、`pattern`、`path`、`query` などの主な値を出し、当たる値が無ければ入力を JSON で出す。
- 値は JSON の文字列の書き方で逃がす。改行は `\n` になるので、命令の中に偽の `pending:` 行を書いても1行に収まる。
- 400字を超える値は切り、`…(+N字)` を付ける。入力が無いときは `(中身なし)` と出す。
- 子が書いた説明文は `("…")` として後ろに付ける。
- `get_session` の `input` は、文字列の値を2000字で切って返す。Write の content を丸ごと返さないためである。

受け口のひな形の「子の承認に答える」には、中身で判断し、説明文を判断の材料にしないことを書いた。`(中身なし)`、`…(+N字)`、読み取れない命令のときは deny する。

- 受け口が `(中身なし)` や切れた値を見て deny することは、実機では通していない。ひな形に書いただけである。
- vm（Linux）での deny の効き方と、本番の常駐が使う設定ディレクトリでの効き方。
