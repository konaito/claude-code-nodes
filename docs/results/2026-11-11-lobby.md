# 受け口とプロンプト無しの新規セッション（2026-11-11）

## 実装の前に確かめたこと

### SDK の sessionId

- SDK 0.3.318 の `query()` に `sessionId`（UUID）を渡し、入力を8秒止めてから1通目を入れた。claude は 2.1.322。
- init と result の `session_id` は、指定した id と同じだった。jsonl は `~/.claude/projects/-private-tmp-ccn-lobby-exp-work/<指定した id>.jsonl` にできた。
- 1通目を入れる前は、init も jsonl も無かった。claude のプロセスは 2.8 秒の時点で起動していた（`commands_changed` が届いた）。
- 1通目を待つ claude 1体の RSS は約 300MB だった（`ps -o rss` で 309264 KB。ユーザー設定の MCP サーバーの子プロセスは含まない）。
- 遅延起動した形（入力を3秒止めてから1通目）で Bash に `echo $CLAUDE_CODE_SESSION_ID` を実行させると、指定した id が出た。

## 受け口の許可（.claude/settings.json）

前の試しでは、default の受け口に1件の依頼で8回の承認が要った。受け口のディレクトリに許可を置き、手順の書き方も直した。測った claude は 2.1.322、設定ディレクトリは `CLAUDE_CONFIG_DIR=~/.cam/profiles/agent`（本番の常駐とは別）。

### 実装の前に確かめたこと

`claude -p --permission-mode default` を未信頼のフォルダで動かし、無害な命令（`probe`、呼ぶと /private/tmp に1行足す sh）を許す規則の置き場を比べた。

| 規則の置き場 | 結果 |
| --- | --- |
| `.claude/settings.json` | 使われない。stderr に `Ignoring 1 permissions.allow entry from .claude/settings.json: this workspace has not been trusted.` が出た |
| `.claude/settings.local.json` | 使われた |
| `--settings <file>` | 使われた |

公式の文書（permissions の「What runs before you trust a folder」）にも、`claude -p` と SDK のセッションは project の `permissions.allow` を使わないとある。そこでノードは、cwd が受け口のセッション（resume を含む）にだけ、同じ `.claude/settings.json` を SDK の `settings` でも渡す。

規則があっても止まる書き方も、同じ方法で調べた（Read の許可を足した回）。

| 命令 | 結果 |
| --- | --- |
| roots の下を指す `ls`、`head`、`cat`（`Read(//<root>/**)` あり） | 通った。Read の許可が無い回では、作業ディレクトリの外として止まった |
| `git -C <dir> remote -v`、`git -C <dir> log` | 止まった |
| `for d in …; do …; done`、`probe show $CLAUDE_CODE_SESSION_ID` | 「変数を確かめられない」で止まった |
| `probe allow x; probe read y; echo "exit=$?"` | `echo "exit=$?"` で止まった |
| `ls ~/Documents \| head -3` | 止まった |

前の8回の多くは、この書き方によるものだった。ひな形には「1回の Bash に1命令、変数と `~` を使わず絶対パス、remote は `.git/config` を読む」と書き、`~/Documents` は描画のときに絶対パスにした。自分の権限モードは `ccn show`（対象なし）で読めるようにした。

### 置く許可

roots が `/Users/konaito` のときの中身は次のとおり。

```json
{
  "permissions": {
    "allow": [
      "Bash(ccn peers *)", "Bash(ccn ls *)", "Bash(ccn show *)", "Bash(ccn new *)", "Bash(ccn run *)",
      "Bash(ccn read *)", "Bash(ccn allow *)", "Bash(ccn deny *)", "Bash(ccn stop *)",
      "Read(//Users/konaito/**)"
    ]
  }
}
```

git の規則は入れていない。`git -C <dir> remote -v` を許すには `*` を下位命令の前に置くことになり、`-c` で別のプログラムを走らせる形まで通るため。

### 試験ノードでの確認

設定は `{ "name": "permtest", "port": 4392, "roots": ["/private/tmp/ccn-lobby-perm"], "lobby": "/private/tmp/ccn-lobby-perm/lobby" }`。試験用に `projects/notes`（README と remote あり）と `projects/greeter`（README あり、remote なし）を作った。受け口は `ccn new --mode default --as tester` で開き、`ccn run` で依頼を送った。

| 受け口 | 依頼 | 受け口のツール呼び出し | 受け口自身の承認 | 子 | 子の承認 |
| --- | --- | --- | --- | --- | --- |
| `ed49182b` | notes に hello.txt を作る | 9回（ls 3、ccn show、ccn new、ccn read 2、ccn allow、cat） | 0回 | `permtest/234219ec-…`（default、parent `agent:permtest/ed49182b/lobby`） | 1回（Write）。受け口が `ccn allow` で答えた |
| `3bf989e8` | 挨拶を出すほうに usage.txt を作り、remote も返す | 16回（ls 3、head 2、cat の .git/config 2、ccn show、ccn new、ccn read 3、ccn show、ccn allow 2、cat） | 0回 | `permtest/842a0984-…`（default、parent `agent:permtest/3bf989e8/lobby`） | 2回（Write と確かめの Bash）。受け口が `ccn allow` で答えた |

- 承認の回数は、`ccn run` の出力の `[permission]` の行で数えた（2件とも0行）。実際に出た命令の形は、受け口の jsonl で確かめた。
- hello.txt は「こんにちは」、usage.txt は「sh hello.sh で動かす」の1行でできた。
- 子は default のまま Write で承認を求めた。子に受け口の許可が渡らないことは、API の試験（受け口以外の cwd と resume では `settings` が undefined）で固定した。
- 試験ノードのログ（node.log）に、未信頼の警告は出ていない。SDK が claude の stderr をこのログに流すかは確かめていない。

### 片づけ

試験ノードの node セッション4つを `ccn stop` で止め、ノードを pid 指定で止めた。cwd が `/private/tmp/ccn-lobby-perm` の下の claude は残っていなかった。本番の 4323 には触っていない。

### 確かめていないこと

- 本番の常駐が使う設定ディレクトリ（`~/.claude`）と、vm（Linux）での受け口の承認の回数。
- 別の機械の受け口へ受け渡す手順（ひな形の手順3）での承認の回数。
- 受け口が CLAUDE.md の書き方を守らなかったとき（変数やループを書いたとき）は、これまでどおり送り手の承認が要る。
- roots がホームの機械では、`Read(//Users/konaito/**)` によって `~/.config/ccn/ccn.json` や `~/.ssh` も承認なしで読める。秘密の置き場に `Read` の deny を足すかは決めていない。
- `ccn new … --mode bypassPermissions` のように、受け口がひな形と違うモードで子を立てることは、許可の規則では止められない。
- default の送り手は、受け口の `ccn new` と `ccn allow` を見なくなった。`ccn run`、`ccn allow`、`ccn stop` は、受け口の子以外や別のノードのセッションにも当てられる。許可の一覧に書き込み系の規則は無いが、ccn を通した書き込みは承認なしで起こせる。
- 2件目では、子の Bash の承認を受け口が説明文だけで許した。`ccn show` の `pending:` に命令の本文が出ないため。
- 受け口の resume で `settings` が付くことは、API の単体試験だけで確かめた。実機では通していない。
- 子に受け口の許可が渡らないことは、単体試験で固定した。実機では、子が承認を求めた Write と Bash がもともと許可の一覧に無いため、矛盾が無いことまでしか言えない。
